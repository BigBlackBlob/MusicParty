第二批：平台授权与房间隔离

先处理仍可越权读写的入口，并统一授权调用方式，为后续来源管理和封面取色提供基础。

  • 26 / 4 / 5：复用第一批修正后的会话解析，统一启动与在线更新的 allowlist 语义、cookie 凭证来源及并发安全的策略读取。不要在持有策略锁时执行数据库查询。
  • 3 / 13：媒体缓存命中前检查权限，歌单导入复用同一平台授权入口。
  • 1 / 2：房间歌单读取、导出及跨房间入队复用统一房间访问判断，承接第一批的拥有者权限模型。

验收：无权用户读写私有房间均失败；合法 cookie 用户正常访问；权限撤销后缓存仍存在也不能读取；在线修改与重启加载行为一致；策略更新与请求并发时无 race。

第三批：房间更新、改密与删除

这些问题共享房间写事务和权限判断，集中处理可减少多次改动同一服务。

  • 7：区分未提供 isPrivate 与显式 false，保留现有客户端兼容性，不必为此强制迁移整个 API。
  • 25：密码版本在事务内推进，避免并发改密复用版本。
  • 15：创建和重命名执行同一名称规则，并确保并发时规则成立。若增加唯一约束，先明确已有同名数据的迁移处理。
  • 6：删除协调 runtime 关闭、连接清理及持久化写入边界，防止删除后数据重建；参考第一批 28 的协调机制，但独立验证房间删除。

验收：仅改名称不会公开房间；并发改密后旧凭证失效；并发创建/重命名不产生违规同名数据；删除与入队、播放推进交错时，删除后的房间不能继续写入。

第四批：队列恢复、协议与播放顺序

这一批直接对应队列和拖动经常失效的反馈，包含必要的前后端契约修改。

  • 20：先确定队列版本跨 runtime 重建的规则，再同步快照、增量 patch、客户端版本门控。不能只把初始版本设成 1 就视为解决。
  • 18：校验 ping payload，确保异常路径同样注销连接并 detach runtime。
  • 17：校验 mutationId，明确重复命令的确认语义和去重作用范围，避免确认丢失后重试再次执行。
  • 9：统一单曲、批量、HTTP 和 WS 入队的容量限制，明确批量超限采用全部拒绝还是部分接受，以及历史配置控制内存窗口还是持久化保留。
  • 21：建议保留“下一首播放”的承诺，在 shuffle 中也明确优先级；实施前确认单曲与批量置顶、连续置顶的相对顺序。普通拖动是否影响 shuffle 是另一项语义，不要默默改变。

验收：带持久化队列的重启、runtime 回收和重连可恢复；resync 能收敛；重复命令不重复执行；超限不会部分写入未声明的数据；自然结束与手动 next 遵循同一顺序；shuffle 与置顶组合通过确定性的行为测试。

第五批：会话有效期与请求资源控制

  • 16：服务端验证会话有效期，改密撤销其他会话并处理关联 WS；为历史 session 定义迁移或兼容规则，不凭空增加不存在的禁用账号管理功能。
  • 27：修正限流记录过期和满容量策略；代理链从右向左剥离可信代理，选取首个不可信来源，不能简单改成取最右项。
  • 8：访客创建接入有效限流。先清理过期 session；profile 可能拥有歌单和历史，只有明确不存在有效引用时才能回收。
  • 11：落实聊天发送间隔和保留配置，区分私聊房间流与公共聊天流的计数边界。历史保留策略涉及删除，需明确语义再实施。

验收：到期或改密后的 token 无法建立新连接，已有连接按约定撤销；限流 map 满载后新来源仍受控；可信/非可信代理链均正确；清理不会删除仍有归属数据的访客身份。

第六批：本地曲库转码恢复与元数据

以第一批 28 / 29 的删除协调及终止状态保护为基础，先保证状态不丢失，再增加恢复能力。

  • 30：元数据 PATCH 只写允许编辑的字段，不回写状态、输出路径和任务字段。
  • 32：完成状态提交成功后才清理源文件；区分成功提交、写入失败及因删除而未更新，避免误处理回调。
  • 33：禁用曲库时相关读写入口行为明确，避免空 library 调用。
  • 31：最后实现启动恢复，采用有界调度，恢复任务仍受删除状态保护。覆盖源文件存在、缺失和同文件重传。

验收：编辑与转码/删除交错不覆盖状态；写库失败保留恢复材料；重启不会永久卡住 PENDING；启动恢复与删除并发不会复活歌曲；禁用模式不出现 panic。

第七批：Subsonic 管理、协议与封面

  • 38：先原子初始化并回读站点密钥，保留已有密钥；不得覆盖密钥或静默丢弃无法解密的现有来源。
  • 14：明确全局 source 与房间 binding 的所有权和共享规则，原子保存并在提交后更新运行时注册；共享来源更新应同步所有受影响绑定。
  • 36：统一解析 Subsonic status/error，让管理端来源测试反映真实协议结果。
  • 37：修正 albumOffset 并验证第二页。
  • 39：复用第二批的已授权封面读取逻辑；若保留 HTTP 自调用，严格限制目标并安全传递身份。

验收：并发首次保存得到同一密钥；失败事务不留半成品；多房间来源行为一致；保存后重启可解密；HTTP 200 的协议失败不会显示成功；受限封面取色正常且无越权。

第八批：媒体缓存容量与下载边界

34 与 35 共用实际磁盘占用模型，一并完成。启动扫描需考虑缓存文件名是 key 的哈希，无法反推原始 key；应按磁盘文件标识建立可淘汰索引，不要求恢复不可恢复的信息。

对已有成品、在途临时文件及并发下载执行容量控制，限制单文件大小与下载持续时间。下载超时作用于后台缓存任务，避免误把短超时施加到正常媒体播放代理。

验收：旧缓存未再次访问也计入占用；重启后上限有效；未知长度及超大响应可终止；多个并发临时文件不能突破声明的资源边界；失败和取消正确释放预留空间。

第九批：REST/WS 输入与错误契约

  • 10：统一音乐对象校验和批量上限，复用第四批已确定的容量及批量语义，不重复实现规则。
  • 12：对分页参数执行范围校验，内部 provider 调用也不能绕过必要边界。
  • 19：输入问题返回稳定 4xx，保留上游错误与内部错误的区别。

验收：同类 REST/WS 请求得到一致结果；畸形、超长、超量和边界分页值不会写入无效数据或发出不合理上游请求；schema、生成类型与实际错误响应一致。

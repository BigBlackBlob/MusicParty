# Spotify Embed Playback Integration Plan

Add Spotify as a default-off experimental source for self-hosted MusicParty rooms. Each listener opts in with their own Spotify Premium account and streams directly from Spotify through the Web Playback SDK. MusicParty shares track and transport state over WebSocket. Go uses an operator-owned Spotify app for catalog search and track resolution. Server-side audio decoding and audio relay are outside scope. Section 10 records the policy ambiguity to confirm before a public or commercial release.

## 1. Credential model

- **Operator app.** Register an app in the Spotify Developer Dashboard for Web API and Web Playback SDK access. Use its client ID and secret for Client Credentials. In `backend-go/internal/platform/spotify/token.go`, exchange them at `POST https://accounts.spotify.com/api/token` with `grant_type=client_credentials` and HTTP Basic authentication. Keep the app bearer in process memory. Use the response's `expires_in`, renew on demand within 60 seconds of expiry, and coalesce concurrent renewals. If Spotify rejects a catalog bearer with `401`, invalidate that bearer, reacquire once, and retry the request once. [Client Credentials](https://developer.spotify.com/documentation/web-api/tutorials/client-credentials-flow)
- **Operator rotation.** Read the app credentials from the environment at startup. Rotate the secret in the dashboard and redeploy or restart with the replacement so the process drops its token cache. Rotate the browser's public client ID only when changing apps. Existing grants belong to the old app, so members reconnect after a client ID change. Spotify does not implement `platform.CredentialUpdater` or add keys to `loadPlatformSettings`, `isPlatformCredential`, or `updatePlatformCredential` (`backend-go/internal/platform/model.go:85`, `backend-go/cmd/musicparty/main.go:298`, `backend-go/internal/store/sqlite/credentials.go:196`, `backend-go/internal/httpapi/admin.go:62`).
- **Member playback uses option (a), direct browser PKCE.** In a proposed `music-party-web/src/composables/useSpotifyAuth.ts`, start authorization after the member selects **Connect Spotify**. Use Web Crypto for a random single-use `state` and an S256 challenge. Keep only the pending state, verifier, expiry, and validated same-origin room return path in tab-scoped `sessionStorage` for the redirect. On return, consume the pending record, validate state and expiry, scrub the OAuth query from the address bar, and exchange the code directly with Spotify from the browser. Request `streaming` and `user-modify-playback-state`. The former is for the SDK, and the latter is for starting a URI on the member's SDK device. [PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow) · [Scopes](https://developer.spotify.com/documentation/web-api/concepts/scopes)
- **Member token lifetime.** Keep the access and refresh tokens in module memory outside persisted stores, telemetry, cookies, and WebSocket payloads. Coalesce refreshes and check `expires_in` before handing a token to the SDK or sending a playback request. Adopt a replacement refresh token when Spotify returns one. Keep the current refresh token when Spotify omits it. On `invalid_grant`, clear the in-memory grant and prompt the member to reconnect. Disconnecting or signing out clears the grant and disconnects the local player. A full page reload requires reconnecting. Go never receives, stores, or distributes member tokens. [Refreshing Tokens](https://developer.spotify.com/documentation/web-api/tutorials/refreshing-tokens)

## 2. Platform package

- Add `backend-go/internal/platform/spotify/spotify.go`, `token.go`, and focused tests. The `Service` holds a `*platform.Client`, feature flag, operator app credentials through its token provider, and test-injectable catalog and token base URLs. Use fixed Spotify origins in production. Assert `platform.Service` and `platform.PlayableResolver`. `Name()` returns `spotify`. `Available()` checks enabled and configured credentials locally, with upstream auth or rate-limit failures reported by the operation that encountered them. Embed or reuse `platform.Unsupported` for out-of-scope methods (`backend-go/internal/platform/model.go:14`, `:28`, `:73`, `:102`).
- Copy QQ's feature-gated constructor and bounded response handling (`backend-go/internal/platform/qq/qq.go:16–38`, `:49–78`). Follow Netease's validation, typed catalog mapping, and canonical detail lookup before queueing (`backend-go/internal/platform/netease/netease.go:108–135`). Spotify calls its official Web API directly. Use request timeouts, cancellation, bounded JSON decoding, redacted errors, and no credential-bearing redirects. Handle `429` with `Retry-After` where provided and surface quota exhaustion without a retry loop. [Rate Limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits)
- `Search(ctx, keyword, offset, limit)` uses `platform.ValidateSearch` and `GET /v1/search` with `type=track`, encoded `q`, `offset`, `limit`, and an explicit `market`. Use `US` as the initial documented catalog market with no new env var. An app token has no user country. Catalog availability in that market does not establish availability for each listener. Spotify's current Dev Mode search cap is 10 per upstream request. Preserve the existing MusicParty pagination contract by fetching bounded batches of up to 10 for larger requests, stopping at Spotify's documented offset ceiling or at the last page. Map ID, name, artist names, `duration_ms`, album art, and `Platform: "spotify"` into `platform.Music`. The existing interface needs no room or session input. [Search](https://developer.spotify.com/documentation/web-api/reference/search) · [Dev Mode Migration Guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide)
- `ResolvePlayable` validates the requested track ID, looks up `/v1/tracks/{id}` using the app token and catalog market, and validates the returned metadata and canonical track URI. Return `PlayableMusic` with the canonical `Music`, `PlayerType="spotify-embed"`, `EmbedID="spotify:track:<id>"`, and an empty `URL`. Preserve the API-provided canonical URI when Spotify relinks a track. Follow YouTube and SoundCloud's embed resolver pattern (`backend-go/internal/platform/youtube/youtube.go:95–118`, `backend-go/internal/platform/soundcloud/soundcloud.go:142–147`). [Get Track](https://developer.spotify.com/documentation/web-api/reference/get-track) · [Track Relinking](https://developer.spotify.com/documentation/web-api/concepts/track-relinking)
- Bypass `proxyPlatform` and `media.Proxy` for Spotify audio (`backend-go/internal/httpapi/media.go:334`). The required `StreamURL` method returns the existing unsupported/no-stream result. Omit `MediaSource` and `StreamCacheable` because the service has no stream URL to serve or cache. Add no stream endpoint. Update the `PlayableMusic` comment to document an empty URL for embeds and a track URI for Spotify's `EmbedID`.
- Register the service beside QQ in `backend-go/cmd/musicparty/main.go:78–99`. Add `spotify` to the explicit platform order in `backend-go/internal/httpapi/platforms.go:262–277`. Extend the embed URL-clearing branch in `backend-go/internal/realtime/runtime.go:1289–1302` to cover `spotify-embed`. Preserve `PlayerType` and `EmbedID` through the queue write, reload, queue snapshot, and `nowPlaying` paths (`backend-go/internal/httpapi/websocket.go:571`, `backend-go/internal/store/sqlite/models.go:80–94`, `backend-go/internal/realtime/runtime.go:1332–1373`).

## 4. Frontend embed player

- Add `music-party-web/src/components/SpotifyPlayerAdapter.vue`. In `AudioEngine.vue:39` and `:86–88`, add the `spotify-embed` branch and include it in the external-player guard so native playback and preloading do not run. Follow the lifecycle pattern in `YouTubePlayerAdapter.vue` and `SoundCloudPlayerAdapter.vue`. Use typed SDK bindings for the subset consumed by this adapter. Keep OAuth state in `useSpotifyAuth.ts` so switching sources does not discard the grant.
- After the member opts into Spotify audio, load `https://sdk.scdn.co/spotify-player.js` once and wait for `window.onSpotifyWebPlaybackSDKReady`. Instantiate `new Spotify.Player({ name, getOAuthToken, volume })` with the member's in-memory token callback. Register listeners before calling `connect()`. Use the `ready` event's `device_id` and discard it on `not_ready`. Call `activateElement()` from an explicit **Enable Spotify audio** gesture to account for browser autoplay rules. [SDK Getting Started](https://developer.spotify.com/documentation/web-playback-sdk/tutorials/getting-started) · [SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- The SDK exposes `pause()`, `resume()`, and `seek(positionMs)`. To load a new URI, make a browser-side `PUT https://api.spotify.com/v1/me/player/play?device_id=…` with the member's bearer, a one-track `uris` array, and the target `position_ms`. Always target the device ID received from that tab's `ready` event. Confirm the track from `player_state_changed` or `getCurrentState()` before a follow-up seek or pause. [Start/Resume Playback](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback) · [SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- Keep SDK playback status local and give each listener a **Leave Spotify audio** control. On track or room changes, discard stale work. Pause the SDK device and remove listeners and timers before switching to another source. Disable crossfade or intentional overlap at either Spotify boundary. Retain consent in page memory until disconnect or sign-out. Show Spotify attribution and a link back to the track using its canonical Spotify ID. [Developer Policy, section II](https://developer.spotify.com/policy) · [Spotify URIs and IDs](https://developer.spotify.com/documentation/web-api/concepts/spotify-uris-ids)

## 5. Sync model

- **Go owns the room timeline.** Continue broadcasting `player.state`, including `nowPlaying.music.embedId`, `currentPosition`, `serverTimestamp`, `isPaused`, `queueId`, `playEpoch`, and `stateVersion`. Existing room controls still send play/pause, seek, and skip through MusicParty. Use the established state ordering in `music-party-web/src/domains/realtime/roomStateSynchronizer.ts:48–99`. The backend issues no Spotify playback command and makes no Spotify API request on behalf of a member (`backend-go/internal/realtime/runtime.go:1350–1373`).
- **Start the Spotify room clock server-side.** Current queue activation sets `ready`, which holds the position until a playback report or a timeout (`backend-go/internal/realtime/runtime.go:1001–1019`, `:1326–1331`, `:1465–1478`, `:1556–1644`). For Spotify, start a playing track's clock from the committed room timestamp and anchor, including on restore and unpause. Reuse the duration-based advance path and retain the anchor while paused. Fence Spotify playback reports in `ReportPlayback` before they can change the room, including reports from old clients. The adapter does not send native `playback.started`, `playback.stalled`, `playback.ended`, or `playback.error` messages through `useAudioPlayerAdapter.ts:40`. The room advances even when every browser is silent. Keep existing behavior for other sources.
- **Every connected browser follows the same state.** On a new queue item or epoch, load its URI on that browser's device. For a playing track, compute the expected position from the latest snapshot and elapsed server time, clamp it to track duration, and pass it as `position_ms` on start. After confirming the URI, call `seek()` to the latest expected position if startup drift warrants it, then match pause/resume. For a paused mid-track join, keep the expected position locally and defer the initial Spotify start until room resume. The SDK has no documented silent preload operation. [Start/Resume Playback](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback) · [SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- Reconcile on newer snapshots, device readiness, reconnect, and tab visibility changes. Serialize device operations per tab. Reconcile to the latest queue ID and epoch after any in-flight command, including rapid skips between two copies of the same track. Seek immediately on a room seek and correct drift only above a threshold with a cooldown. Use a starting threshold of 1.5 seconds and adjust it from the spike. Room skip selects a new URI through queue state. Local SDK events can measure drift and display readiness. They never advance or pause the room. Treat playback that moves to another Spotify Connect device as local interruption and ask the member to re-enable audio.
- Members who are unconnected, Free, or locally failed receive the same queue, controls permitted by their MusicParty role, and transport state. Their browser produces no Spotify audio. Other members continue normally. A room has no Spotify leader or shared token.

## 6. CSP and HTTPS

- Serve the SPA and OAuth callback over HTTPS and preserve secure WebSocket (`wss:`) connectivity. Register the exact HTTPS callback. Spotify permits HTTP for loopback IP literal redirects and rejects `localhost` redirect URIs. Use an HTTPS test origin for the SDK acceptance pass. [Redirect URIs](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri) · [SDK Getting Started](https://developer.spotify.com/documentation/web-playback-sdk/tutorials/getting-started)
- Add `https://sdk.scdn.co` to `script-src`. Add `https://accounts.spotify.com` and `https://api.spotify.com` to `connect-src` for browser token exchange/refresh and playback control. Retain the site's existing script protections, same-origin APIs, and room WebSockets. If the host separates `script-src-elem` from `script-src`, allow the SDK script in the effective element directive as well. [SDK Getting Started](https://developer.spotify.com/documentation/web-playback-sdk/tutorials/getting-started) · [PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow) · [Start/Resume Playback](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback)
- The current Go static handler, Vue app, and checked deployment files contain no CSP directive to edit. Inspect headers from the actual SPA host or reverse proxy. These additions cover the script and explicit requests owned by MusicParty. Run a report-only CSP pass for the SDK's internal HTTPS, WebSocket, frame, and media requests and allow only origins the pass confirms. A top-level SDK player does not require a MusicParty-created Spotify iframe. If the SPA itself is hosted in a cross-origin iframe, verify `encrypted-media` and `autoplay` permissions. [SDK Overview](https://developer.spotify.com/documentation/web-playback-sdk)

## 7. Premium requirement and failure modes

| Local status | Detection and member action |
| --- | --- |
| `spotify-auth-required` | No browser grant, denied or expired authorization, revoked consent, or refresh rejected with `invalid_grant`. For SDK `authentication_error` or playback API `401`, try one refresh before prompting the member to reconnect. Offer Connect or Reconnect Spotify. A MusicParty login alone provides no Spotify grant. |
| `spotify-premium-required` | A valid member grant reaches the SDK and `account_error` establishes the Premium requirement. An explicitly identified Premium entitlement rejection from Spotify also qualifies. Offer reconnecting with a Premium account. |
| `spotify-access-denied` | Spotify rejects the playback operation with an authorization error whose cause is not established as Premium. Check the Dev Mode allowlist and granted scopes. A bare `403` is insufficient to tell a Free account from an allowlist or scope issue. |
| `spotify-gesture-required` | `autoplay_failed` or activation is pending. Offer **Enable Spotify audio** and catch up after the gesture. |
| `spotify-sdk-unavailable` | Script load, `initialization_error`, unsupported DRM/browser, or device `not_ready`. Show a local retry or supported-browser prompt. |
| `spotify-playback-unavailable` | `playback_error`, device interruption, or a track restricted for that listener. Show the affected track and allow local retry. Honor `Retry-After` for transient rate limits. |

The SDK requires Premium for each listening member. An app owner in Dev Mode also needs Premium for the app to function. Guests and Free members can remain in the room with metadata and queue access and no Spotify audio. The experiment has no 30-second preview fallback. Keep member-specific errors out of room failure and skip paths. [SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference) · [Quota Modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)

## 9. Testing strategy

- **Go catalog tests.** Use `httptest` with injectable token and API origins. Verify form and Basic auth for the app grant, bearer reuse for catalog calls, encoded search and market parameters, pagination across the upstream 10-result cap, typed track mapping and canonical URI, and an empty media URL for resolve. Cover disabled or incomplete config, invalid/unavailable IDs, upstream `401` and `429`, response limits, and redacted errors.
- **App token rotation tests.** Use a fake clock and mocked Accounts endpoint to prove reuse before the refresh window, one concurrent reacquisition near expiry, single retry after a stale `401`, and acquisition with replacement credentials after rebuilding the service. Include config serialization coverage proving that only the public client ID is exposed.
- **Room regression tests.** Use existing Go runtime and HTTP fixtures to check search routing and queue/save/restore serialization. Verify Spotify's clock starts without clients, pause/seek/restore preserve the correct position, the server advances at track end, and stale or failed client reports cannot change the Spotify epoch or advance the queue. Exercise an existing native source through the normal clock-owner path to catch regressions from the new branch.
- **Manual SDK verification.** On an HTTPS test instance, use two allowlisted members on distinct Premium accounts and a guest with no Spotify connection. Confirm individual consent, correct browser device targeting, startup after a gesture, pause/resume, forward/back seek, skip, late join while playing and while paused, reconnect after WebSocket loss, and per-member recovery after disconnecting Spotify Connect. Test a Free account and an unallowlisted account separately and check that neither advances the room. Let an access token expire in an open tab and check refresh. Reload and check reauthorization. Verify token and callback-code handling in browser storage, URL, WebSocket traffic, and server logs. Measure drift and collect CSP reports in target browsers. Automated browser tests for the SDK belong to the later frontend-test task.

## 10. Risks and unknowns

- **Policy risk to confirm before public release.** Section III.4 addresses non-interactive webcasting and illustrates it with one source serving simultaneous listeners. Individual member consent, interactive room controls, and direct per-account SDK streams make this the most defensible design for MusicParty. Spotify Jam's remote listening is a first-party analogy. The published text gives third parties no explicit carve-out for coordinated playback, and III.11's restriction on replicating a core Spotify experience may apply to synchronized rooms. Section III.5 also warrants specific confirmation for a room that queues sources from other services. Section III.6 addresses synchronization of recordings with visual media. MusicParty's assessment is low risk for a default-off, noncommercial, small self-hosted experiment within the Dev Mode allowlist. The published policy remains ambiguous for this use case. Proceed with experimental implementation and recommend that operators seek written confirmation covering coordinated playback, mixed-source queues, the audience, and any commercial use before a public or commercial release. Both the policy and the SDK reference restrict commercial streaming uses. [Developer Policy, sections III–IV](https://developer.spotify.com/policy) · [Spotify Jam](https://support.spotify.com/us/article/jam/) · [SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- **Validate the documented browser path on a fresh Dev Mode app.** Spike direct PKCE exchange and refresh, `Spotify.Player` construction, user-gesture activation, and a browser-origin start request against its own `device_id` with the two playback scopes. Confirm the device can start without unexpectedly taking over another device, and determine how to distinguish market restrictions, access denials, and device loss using the documented signals. The public OAuth guides document no device-code grant. Shared-account or shared-token concurrency is outside scope. Test separate accounts across browsers and check duplicate-tab behavior, autoplay, private browsing, background throttling, and drift. [Spotify Authorization](https://developer.spotify.com/documentation/web-api/concepts/authorization) · [SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference) · [Start/Resume Playback](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback)
- **Catalog and deployment.** Verify search and detail lookups with the operator's app, the effective market, and the current Dev Mode quota limits. Measure request costs before adding any caching beyond the app token. Keep the CSP rollout and browser compatibility claims tied to the HTTPS spike. [Search](https://developer.spotify.com/documentation/web-api/reference/search) · [Quota Modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)

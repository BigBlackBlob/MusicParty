# MusicParty 性能与稳定性综合优化计划

**制定日期**: 2026-07-26  
**基线分支**: `NRT-Base`  
**基线提交**: `8b51512`  
**目标部署**: 单实例 SQLite、中型自托管

## 1. 综合结论

结合现有性能审计、修复进度文档和远端代码实际状态，系统已经完成部分正确性与稳定性修复，但性能审计中的核心优化仍多数未完整落地。

最值得优先解决的不是直接引入大型连接池，或把所有 `synchronized` 替换成读写锁，而是：

1. 建立可量化的性能基线。
2. 消除无界 WebSocket 和房间命令队列。
3. 避免每次队列操作完整重写 SQLite。
4. 避免广播完整队列和重复 JSON 序列化。
5. 隔离数据库、文件和外部进程等阻塞工作。
6. 对外部平台和下载任务增加明确的并发边界。

## 2. 已确认边界

- 队列增删、排序等操作必须在 SQLite 事务提交后再向客户端 ACK。
- 允许升级 WebSocket 协议，不要求兼容旧版前端的完整队列数组协议。
- 慢客户端的可靠事件队列溢出时允许断开，通过重连和快照恢复。
- 未来 1-2 年按单实例 SQLite 部署优化。
- 目标规模为 1-2 CPU、1-2GB 内存、100-300 个 WebSocket、10-30 个活跃房间。
- 完整 1000 首队列可以浏览，但只允许前 50 首交互排序。
- 使用 Micrometer 和 Prometheus 作为主要可观测性方案。
- 本地缓存下载按平台设置有限并发，并保留全局并发上限。

## 3. 当前状态

| 领域 | 当前状态 | 主要缺口 |
| --- | --- | --- |
| SQLite | 部分完成 | 已启用 WAL、NORMAL、busy timeout；仍无适合 SQLite 的连接和写入模型 |
| 队列持久化 | 高风险 | 每次操作删除并逐条重建整个房间队列 |
| 队列锁 | 正确但粗粒度 | 单房间 `synchronized`，暂时不是首要瓶颈 |
| WebSocket 序列化 | 未完成 | 同一广播对每个客户端重复序列化 |
| WebSocket 背压 | 未完成 | 每个客户端使用无界缓冲，且发送结果未处理 |
| 房间命令队列 | 部分完成 | 已按房间串行，但待处理队列无界 |
| 队列可靠性 | 部分完成 | 排序有 ACK/NACK，其他操作缺少统一确认协议 |
| 队列版本 | 存在漏洞 | 完整 `player.state` 可能覆盖较新的队列版本 |
| LocalCache | 部分完成 | 有配置检查，但底层队列仍无界且容量检查非原子 |
| Scheduler | 未完成 | JDBC、文件、FFmpeg、yt-dlp 竞争全局 `boundedElastic` |
| 外部 API | 部分完成 | 缺少统一 bulkhead、分类重试、断路器和请求合并 |
| 前端队列 | 未完成 | 最多渲染 1000 个组件，每次更新替换完整数组 |
| 可观测性 | 基础状态 | 有 Admin 快照，无延迟、队列深度、丢弃和错误指标 |
| 性能测试 | 未完成 | 没有可重复执行的负载和回归基准 |

## 4. 阶段 0：性能基线与正确性护栏

**预计时间**: 2-4 天

这是所有优化的前置条件。先测量，再修改。

### 4.1 实施内容

1. 接入 Micrometer 和 Prometheus Registry。
2. 增加关键指标：
   - WebSocket 在线连接数。
   - 每种消息的广播次数、字节数和序列化耗时。
   - WebSocket 消息合并、丢弃、发送失败和慢客户端断开次数。
   - 每个房间命令队列深度、等待时间和执行时间。
   - 队列长度、变更类型、落库行数和事务耗时。
   - SQLite `BUSY`、锁等待和失败次数。
   - 下载 queued、active、rejected、failed、completed。
   - 每个平台外部 API 的并发量、P95 延迟、超时、重试和断路次数。
   - JVM heap、GC、线程及自定义 Scheduler 队列。
3. 修正现有 `activeRoomCount` 含义，区分：
   - 已持久化房间。
   - 已加载房间。
   - 当前活跃播放房间。
4. 建立可重复负载脚本：
   - 10、100、300 个 WebSocket。
   - 一个故意不消费消息的慢客户端。
   - 100、500、1000 首队列。
   - 单房间和 20 房间并发操作。
   - 上游超时、429、500 模拟。
5. 建立前端性能基准：
   - 1000 首队列初次渲染。
   - 单条状态更新。
   - 前 50 首拖拽。
   - 连续队列事件处理。

### 4.2 第一版验收目标

- 300 个连接下，内存不会因为慢客户端持续增长。
- 500 首队列操作 ACK P95 小于 250ms。
- WebSocket 状态收敛时间小于 2 秒。
- 所有内部队列都有可观察的容量和深度。
- 后续优化能够提供修改前后对比数据。

## 5. 阶段 1：WebSocket 稳定性与广播效率

**预计时间**: 4-6 天

主要涉及：

- `ReactiveSocketBroker`
- `WebSocketBroadcaster`
- `RoomCommandCoordinator`
- `MusicSocketController`
- 前端 `socket.js`、`socketHandler.js`、`player.js`

### 5.1 广播只序列化一次

将同一个广播消息从“每个客户端分别序列化”改为“一次 JSON 序列化后复用字符串”，并记录序列化字节数和耗时。

### 5.2 消息分类

可合并状态：

- `player.state`
- `player.queue`
- 在线成员列表
- 房间列表
- 播放进度

可靠事件：

- 队列操作 ACK/NACK
- 聊天消息
- 房间删除
- 登录和权限变化
- 管理操作结果

可合并状态只保留最新版本；可靠事件不得静默丢弃。

### 5.3 有界客户端发送队列

- 每个客户端设置固定容量。
- 状态消息允许覆盖旧状态。
- 可靠事件队列满时断开慢客户端。
- 客户端重连后主动获取完整快照。
- 检查并处理每次 `tryEmitNext()` 返回值。
- 容量通过阶段 0 压测确定，并保持可配置。

### 5.4 有界房间命令队列

`RoomCommandCoordinator` 增加：

- 每房间最大待处理命令数。
- 排队超时。
- 队列满时返回明确 NACK。
- 房间关闭时，所有待处理 Future 异常完成。
- 命令等待时间和执行时间指标。

### 5.5 修复版本一致性

完整状态和队列事件统一携带版本：

```json
{
  "roomId": "lounge",
  "stateVersion": 120,
  "queueVersion": 42
}
```

客户端规则：

- 旧版本直接忽略。
- 版本断层时请求完整快照。
- 无版本状态不得覆盖较新的队列。

### 5.6 重连优化

- 指数退避增加 jitter。
- 浏览器离线时停止计时重连。
- `online` 事件触发即时重连。
- 重连后先获取快照，再恢复常规事件处理。

### 5.7 验收标准

- 同一房间广播只发生一次 JSON 序列化。
- 所有发送队列和命令队列有明确容量。
- 慢客户端压测下内存稳定。
- 房间关闭不会留下永不完成的命令。
- 任意事件乱序下，客户端最终队列版本正确。

## 6. 阶段 2：队列增量协议与 SQLite 写入优化

**预计时间**: 1-2 周

这是预期收益最大的阶段。

### 6.1 队列操作统一 ACK

所有队列变更采用：

```text
客户端 mutationId
-> 服务端按房间串行执行
-> SQLite 事务提交
-> ACK + 新 queueVersion
-> 广播增量事件
```

需要覆盖：

- 添加歌曲。
- 删除歌曲。
- 批量删除。
- 置顶。
- 批量置顶。
- 排序。
- 清空。
- 状态更新。

任何数据库失败都必须 NACK，不能先向客户端报告成功。

### 6.2 停止完整重建队列

当前普通操作会删除房间队列并逐行重新插入。改为与领域操作对应的增量 SQL：

- 添加：单行 `INSERT`。
- 删除：按 `queue_id` 删除。
- 批量删除：批量 SQL。
- 状态变化：单行 `UPDATE`。
- 清空：房间级 `DELETE`。
- 排序：只更新受影响范围。

完整 `replaceQueue()` 仅保留给旧数据迁移、恢复、管理员修复和测试夹具。

### 6.3 排序键策略

建议采用带间隔的整数排序键：

```text
1000, 2000, 3000...
```

拖动时优先取相邻键之间的中间值，空间不足时才对局部范围重新编号。

这使普通拖动通常只更新一行；只允许前 50 首交互排序后，局部重排成本也可控。

### 6.4 增量 WebSocket 协议

示例：

```json
{
  "type": "queue.patch",
  "roomId": "lounge",
  "queueVersion": 43,
  "operation": "move",
  "queueId": "q-123",
  "targetQueueId": "q-456",
  "position": "before"
}
```

其他操作对应 `append`、`remove`、`status`、`clear`。客户端发现收到的版本不是当前版本加一时，立即请求完整快照。

### 6.5 批量 JDBC

仍需要重建时统一使用 `JdbcTemplate.batchUpdate()`，并优化：

- 队列恢复。
- 历史记录恢复。
- 房间歌单排序。
- 用户歌单排序。
- 批量导入。

删除歌单排序中重复的两轮更新。

### 6.6 SQLite 完整性

- 启用 `foreign_keys=ON`。
- 队列 `(room_id, queue_id)` 保持唯一。
- 歌单排序键增加适当唯一约束。
- 排序和序号分配必须置于同一事务。

### 6.7 验收标准

- 单曲添加、删除和拖动通常只写入 1-3 行。
- 500 首队列操作 ACK P95 小于 250ms。
- 1000 首队列下，普通操作耗时不再随队列长度线性增长。
- SQLite 写失败时客户端收到 NACK，并恢复服务端快照。
- 增量消息丢失、重复或乱序时，客户端能通过版本检测恢复。
- 所有外键和排序约束均有迁移测试。

## 7. 阶段 3：SQLite 连接与阻塞任务隔离

**预计时间**: 4-6 天

### 7.1 SQLite 连接模型

不建议直接配置 10 个 Hikari 连接。单实例 SQLite 依然只有一个主要写入者，连接过多可能增加锁竞争。

建议起始配置：

- HikariCP 最大连接数：3。
- 最小空闲连接：1。
- 连接超时：5 秒。
- SQLite `busy_timeout`：5 秒。
- 保留 WAL 和 `synchronous=NORMAL`。
- 一个专用、有界的数据库写入执行器。
- 读取允许有限并发。
- 所有写事务保持尽可能短。

最终连接数通过压测比较无连接池、2、3、4 个连接的结果决定，重点观察 `SQLITE_BUSY`、P95 延迟、事务吞吐和内存。

### 7.2 专用调度器

| 调度器 | 用途 | 初始建议 |
| --- | --- | --- |
| DB writer | SQLite 写事务 | 1 线程，有界队列 |
| DB reader | SQLite 查询 | 2-3 线程 |
| File I/O | 缓存、上传、元数据读取 | 4-8 线程 |
| Subprocess | FFmpeg、yt-dlp | 2-4 线程 |
| Image CPU | 封面解码和取色 | 接近 CPU 核数 |

所有参数通过配置提供，不写死。

### 7.3 Reactor 调度审计

- 阻塞源使用 `Mono.fromCallable(...).subscribeOn(...)`。
- 不使用 `publishOn()` 掩盖上游阻塞。
- WebClient 原生异步调用不无理由切到阻塞线程池。
- JSON 小消息解析一般不进入 `boundedElastic`。
- JDBC、文件和进程等待不能回到 Netty event loop。

### 7.4 生命周期管理

- 移除静态 Scheduler 和 Executor。
- 使用 Spring Bean 管理线程池。
- 应用关闭时执行 `dispose()` 或 `shutdown()`。
- 暴露活跃线程、排队任务和拒绝次数。
- 测试结束后不遗留后台线程。

### 7.5 验收标准

- SQLite 写操作只进入单一有界写通道。
- 文件、数据库和外部进程不会耗尽同一个线程池。
- 所有执行器均有容量、拒绝策略和指标。
- 应用关闭后没有未释放的自定义线程。
- 慢下载不会明显提高队列 ACK 延迟。

## 8. 阶段 4：LocalCache 和下载任务稳定性

**预计时间**: 4-6 天

### 8.1 原子容量控制

采用：

```text
原子预留容量
-> 原子注册 musicId 任务
-> 入有界队列
-> 失败时释放容量
```

同一个音乐 ID 的并发请求共享同一任务结果，不重复下载。

### 8.2 按平台 worker pool

| 平台 | 初始并发 | 备注 |
| --- | ---: | --- |
| Netease | 2 | 主要是解析和缓存 |
| Bilibili | 1 | 降低限流和带宽冲击 |
| YouTube/yt-dlp | 1 | 外部进程资源较高 |
| Local/Navidrome | 2 | 根据是否需要转码调整 |
| 全局上限 | 3-4 | 避免 1-2 CPU 环境过载 |

并发值必须可配置。

### 8.3 下载状态

至少区分：

- queued
- resolving
- downloading
- transcoding
- completed
- failed
- rejected
- cancelled
- retry-wait

### 8.4 分类重试

仅对幂等、临时错误重试：

- 网络连接重置。
- 超时。
- 部分 5xx。
- 429，并遵循 `Retry-After`。

不重试：

- 401/403。
- 确认的版权限制。
- 资源不存在。
- 参数错误。
- 用户取消。

使用指数退避和 jitter，并设置最大总耗时。

### 8.5 外部进程控制

- FFmpeg 和 yt-dlp 设置硬超时。
- 超时后终止子进程。
- 标准输出和错误输出使用专用执行器读取。
- 限制进程输出日志长度。
- 应用关闭时清理仍在运行的子进程和 `.part` 文件。

### 8.6 用户反馈

队列满或平台不可用时返回明确状态，例如下载队列已满、平台限流、正在重试、下载失败或已有相同任务执行中。

### 8.7 验收标准

- 下载队列容量是硬上限。
- 同一音乐 ID 不会产生重复任务。
- 一个平台故障不会阻塞其他平台。
- 所有外部进程都有超时和清理机制。
- 下载风暴下 heap 保持有界。
- 队列满时客户端收到结构化错误。

## 9. 阶段 5：外部 API 韧性

**预计时间**: 1 周

### 9.1 平台级 Bulkhead

为 Netease、Bilibili、YouTube、Navidrome 分别设置最大并发请求、最大等待队列、获取许可超时，以及独立失败率和延迟指标。

### 9.2 In-flight 请求合并

适合合并的操作：

- 歌曲详情。
- 歌词。
- Bilibili CID/WBI 元数据。
- 封面下载。
- 播放地址解析。

相同 key 的并发调用共享同一个 `Mono` 或 Future，完成后移除。

### 9.3 TTL 缓存

可以缓存：

- 歌曲和专辑元数据。
- 歌词。
- 搜索结果的短期结果。
- 封面。
- 确认不存在资源的短期负缓存。

谨慎缓存带签名播放 URL、用户权限结果和动态 Cookie 状态。缓存按权重或字节数限制，而不是只按条目数。

### 9.4 断路器

每个平台独立断路：

- 搜索和元数据允许返回仍有效的缓存。
- 播放地址只有确认有效时才返回缓存，否则明确失败。
- 平台认证失败标记配置失效，不自动重试。
- 不将错误伪装成空搜索结果。

### 9.5 WebClient 连接池

显式配置 Reactor Netty `ConnectionProvider`：

- 最大连接数。
- pending acquire 上限。
- pending acquire timeout。
- 空闲和生命周期上限。
- pool 指标。

### 9.6 验收标准

- 单个平台持续超时时，其他平台和房间操作仍正常。
- 相同资源的并发请求只触发一次实际上游调用。
- 429 重试遵循服务端退避时间。
- 断路状态、重试次数和缓存命中率可观测。
- 所有重试均有总耗时和次数上限。

## 10. 阶段 6：前端队列与渲染优化

**预计时间**: 5-8 天

### 10.1 队列虚拟滚动

- 完整 1000 首队列仍可浏览，但只渲染可见区域。
- 前 50 首允许拖拽。
- 第 51 首之后只读浏览。
- 可提供“置顶到可交互区”操作。
- 小队列可关闭虚拟化，保持简单交互。

### 10.2 队列增量应用

客户端按 `append`、`remove`、`move`、`status`、`clear` 和 `snapshot` 应用事件，不再为每次变化替换完整数组。

不变的歌曲对象保持引用稳定，减少 Vue 组件重渲染。

### 10.3 更新批处理

- 同一帧多条状态事件合并为一次 Pinia 更新。
- 使用 `requestAnimationFrame` 批量刷新 UI。
- 状态类消息只保留最新版本。
- ACK/NACK 等交互结果立即处理。

### 10.4 页面可见性

标签页隐藏时：

- 降低心跳频率。
- 暂停非必要动画。
- 降低播放进度 UI 更新频率。
- 暂停封面取色等辅助任务。
- 恢复可见时请求一次状态同步。

### 10.5 拖拽行为

- 仅前 50 首初始化 Sortable。
- 拖拽前记录 `queueVersion`。
- 服务端版本变化时拒绝旧拖拽并刷新。
- NACK 或超时后恢复服务端顺序。
- 触摸端保留明确拖拽手柄。

### 10.6 验收标准

- 1000 首队列只创建有限数量的 DOM 节点。
- 单条状态更新不会重新渲染全部队列项。
- 前 50 首拖拽保持流畅。
- 版本冲突时不会保留错误的乐观排序。
- 隐藏标签页显著减少 CPU 和消息处理消耗。

## 11. 阶段 7：锁模型和内部数据结构

**预计时间**: 3-5 天，仅在性能数据证明需要时实施

### 11.1 不直接替换所有读写锁

当前每个房间有独立 `MusicQueueManager`，房间命令也按房间串行。粗粒度 `synchronized` 模型简单且正确。

在以下工作完成前，改为 `ReadWriteLock` 的收益可能有限：

- 移除完整 SQLite 队列重写。
- 移除锁内外的大量复制。
- 降低广播序列化成本。
- 使用增量消息。
- 隔离阻塞任务。

### 11.2 如果仍存在锁竞争

按以下顺序优化：

1. 为 `queueId` 建立 O(1) 索引。
2. 为 `platform:id` 建立重复检查索引。
3. 修改后生成不可变队列快照。
4. 读取方复用快照，不重复复制整个队列。
5. 保持单写入者模型。
6. 最后比较 `synchronized`、`ReentrantReadWriteLock`、单写 actor 加原子快照。

### 11.3 验收标准

- 锁优化必须在基准测试中产生可重复收益。
- 不破坏队列、历史记录和辅助索引的一致性。
- 所有并发测试重复运行稳定。
- 没有性能收益时保留更简单的 `synchronized`。

## 12. 日志与运维

可与阶段 0-3 并行实施。

### 12.1 生产日志

默认日志改为：

```yaml
org.thornex.musicparty: ${LOG_LEVEL:INFO}
```

DEBUG 只通过环境变量临时开启。

- 下载失败日志包含平台、musicId 和阶段。
- 数据库错误包含操作类型和房间 ID，但不记录敏感数据。
- 慢客户端断开记录队列深度和消息类型。
- Cookie、密码、token 和签名 URL 不得写入日志。

### 12.2 Prometheus 告警建议

- WebSocket 发送失败持续增长。
- 慢客户端断开率异常。
- 房间命令队列接近容量。
- SQLite `BUSY` 增长。
- 队列 ACK P95 超标。
- 下载拒绝或失败率过高。
- 外部平台断路器开启。
- Heap 超过 80%。
- 自定义线程池队列接近上限。

## 13. 推荐执行顺序

```text
阶段 0：指标和压测基线
  -> 阶段 1：WebSocket 与命令队列有界化
  -> 阶段 2：队列增量协议与 SQLite 增量写入
  -> 阶段 3：SQLite 连接模型与调度器隔离
  -> 阶段 4：LocalCache 按平台 worker pool
  -> 阶段 5：外部 API bulkhead、缓存和断路器
  -> 阶段 6：前端虚拟滚动和增量状态应用
  -> 阶段 7：有数据支持时再优化队列锁
```

阶段 1 和阶段 2 应连续实施，因为 ACK、版本和增量协议互相依赖。

## 14. 提交拆分建议

## 15. 总体验收目标

面向已确认的中型自托管规模：

- 300 个 WebSocket 客户端稳定运行。
- 20 个活跃房间能够并发操作。
- 慢客户端不会导致 heap 无界增长。
- 500 首队列操作 ACK P95 小于 250ms。
- 1000 首队列浏览保持流畅。
- 前 50 首拖拽响应稳定。
- 普通队列操作不再完整重写数据库。
- 任何内部队列都具有明确容量。
- 单个平台故障不会耗尽全局线程或连接。
- SQLite 写失败不会向客户端错误 ACK。
- 所有状态乱序和断线都能通过版本化快照恢复。
- JVM 在 1-2GB 内存限制下长时间运行无持续增长趋势。

## 16. 工期与首轮范围

完整实施预计需要约 4-7 周。

第一轮建议只实施阶段 0-2：

1. 建立指标与压测基线。
2. 有界化 WebSocket 和房间命令队列。
3. 完成一次序列化、状态合并和版本恢复。
4. 引入队列增量协议。
5. 将普通队列操作改为 SQLite 增量写入。

这部分可以解决当前最明确的稳定性风险和主要性能瓶颈，并为后续连接池、Scheduler、下载并发和锁模型优化提供可信数据。

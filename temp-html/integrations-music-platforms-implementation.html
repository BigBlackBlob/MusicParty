MusicParty 外部音乐平台接入方案

VK 按音频文件接入，不规划 VK Video。QQ 音乐使用非官方 Node.js 项目 @sansenjian/qq-music-api 做受限解析 sidecar；先确认运行稳定性、授权边界与完整音频可用性。Cookie 仅预留为默认关闭的管理员凭据。Bandcamp 验证 Subsonic 兼容性，SoundCloud 和 YouTube 使用各自的官方嵌入播放器。

仓库分析

队列已经支持按平台和曲目 ID 解析
httpapi/websocket.go 在入队时调用 PlatformAPI.ResolvePlayable。平台的 PlayableResolver 返回曲目信息和 MusicParty 内部播放地址。store/sqlite/models.go 的队列与房间快照保存可播放曲目，含 url 和 needsProxy。VK 用稳定曲目 ID 和内部 URL 就能走这套结构。
媒体代理已有 Range 转发，下载缓存要单独控制
httpapi/media.go 的 proxyPlatform 用 authorizedMediaSource 检查来源权限，再由 MediaSource 解析上游地址。media/proxy.go 转发 Range 和成功响应的范围头。目前上游 416 会变成 502。proxyPlatform 和 PlatformAPI.PreResolveMedia 都有全文件缓存提交路径，接 VK 时需要检查播放请求和下一首预热两处。
房间时钟已有裁决逻辑
AudioEngine.vue 和 useAudioPlayerAdapter.ts 通过现有音频事件更新播放器并上报状态。后者是音频引擎访问房间状态的接口。RoomRuntime.ReportPlayback 核对 playEpoch 和 queueId，按实际开始播放设锚点，拒绝过早的结束事件。当前时钟拥有者的重试耗尽可触发推进，因此接入时要验证哪些错误属于单个成员，哪些代表曲目已经不可用。

VK 音频文件接入

数据路径
授权曲目 ID → Go 解析曲目并生成 MusicParty 播放地址 → 房间保存稳定地址 → 浏览器请求地址 → Go 获取授权文件地址并转发音频 → 现有 AudioEngine 播放和同步

先确认授权接口的实际响应

VKCOM 的公开 schema 描述了 MP3 URL、时长和曲目 ID。实际接入还缺具体端点、可用凭据及脱敏样例。首轮用一首授权曲目确认稳定标识、完整时长、文件类型、是否支持 Range、签名有效期和重签规则，并确认接口授权覆盖房间成员通过服务端收听。若接口返回音频字节，验证字节响应是否支持 Range。若返回播放列表、试听或仅单用户可用的凭据，由各自的约束决定是否能进入共享队列。VKCOM 音频对象 schema

最小实现

  1. 在 internal/platform 增加 VK 来源，按实际响应实现曲目解析和媒体读取。稳定 ID 使用上游定义的完整曲目标识，例如样例验证后采用 owner_id 与 id 组合。时长统一为毫秒。授权凭据留在 Go 端。
  2. 注册默认关闭的来源与同源音频路由。首轮用固定授权曲目验证入队，确认上游支持授权搜索之后再发布搜索入口。由后端以曲目 ID 构造或解析目标，限制可请求的 HTTPS 来源和重定向目标。媒体请求沿用现有会话入口，按获批的授权范围检查读取权限。
  3. 入队和快照保存 MusicParty 内部地址。播放时读取签名 URL。确认上游如何表示签名到期后，可在响应尚未写出时刷新一次。首次接入采用流式转发，跳过请求侧全文件缓存和队列预热下载，也避免签名 URL 进入日志、历史或客户端。后续按授权与实际请求量决定是否缓存。
  4. 保持原生播放和 WebSocket 消息结构。请求有合法 Range 时传递上游返回的 206 及范围头。越界时保留 416 和上游的 Content-Range。若上游忽略 Range 而返 200，按实际行为判定首版能否支持同步拖动。RFC 9110 Range 请求

QQ 音乐接入

以社区 Node SDK 做隔离验证

使用 @sansenjian/qq-music-api，研究核对版本为 2.6.0、提交 45d0d275b590d8c3f99270e7f74135873172c71a。优先调用其函数式 SDK（如 search、getMusicPlay），不要把整套 Koa API 暴露到公网。该仓库 README 声明 MIT，同时明示“仅供学习研究，不可商用”，并提示上游字段可能变动；因此项目用途未确认前只能实验性接入、默认关闭，不应进入商业部署。MIT 仅覆盖代码许可，不代表 QQ 音乐内容、账号凭据或房间共享获得授权。源码快照 · Issue #46：云端搜索异常报告

隔离环境匿名实测：搜索「周杰伦」「陈奕迅」可返回结果，但样例热门付费曲目 getMusicPlay 返回 HTTP 200 仍无播放 URL；部分无付费标记曲目得到 128k MP3。两首样例 HTTPS 音频支持 Range，实际时长与搜索结果接近。getSongInfo 样例返回上游 500001，首版不要依赖它，优先使用搜索结果 metadata。这些结果仅代表测试样例，不可推断任意曲目均可播；必须在目标部署网络重新验证，并确认账号权益、授权与平台条款允许共享播放。

Node 与 Go 不能进程内互调。建议 Node sidecar 只封装搜索和播放地址解析，监听 loopback/私有网络，仅允许 Go 调用；Go 侧实现薄的 Service/PlayableResolver/MediaSource 适配，继续做房间权限校验并经 MusicParty 媒体代理提供地址。播放 URL 是短期上游地址，服务端需只接受 HTTPS、校验 host 和每次重定向目标以防 SSRF，并为过期地址设置有限重解析。首版关闭全文件缓存与下一首预下载。SDK 实测地址初始为 HTTP，但上游样例可切换到 HTTPS 并支持 Range；以目标环境验证结果为准。

包要求 Node ^20.17.0 || >=22.9.0；核对环境使用 Node 24.18.0。接入前需确认部署镜像/运行时兼容并固定版本和锁文件。Issue #46 于 2026-09-10 报告搜索在阿里云服务器异常、本地正常；维护者建议使用智能搜索接口，次日作者回报恢复。因此预发布必须从实际服务端出口执行合约测试，不能只凭开发机成功启用。

按接入方式启用凭据入口

保留可选管理员 Cookie 入口，默认关闭；仅当匿名能力不足、用户明确配置且账号权益可用于该场景时再启用。优先通过 SDK 支持的 credential/header 参数传入。若必须使用 Koa app，检查并修正其请求日志，禁止 Cookie 出现在 query string、访问日志或错误追踪中；不要开放 /user/getCookie、/user/setCookie 等管理端点给公网。

现有管理路由只接受网易云和哔哩哔哩，SQLite 也只对已登记凭据键做加解密。启用 QQ Cookie 时，沿用现有加密存储与启动加载，为其增加专属键，并验证管理员授权、缺失/过期、替换、清除、重启恢复和接口不回显。Go 到 Node sidecar 走受限私有通道；凭据、上游播放 URL 不得进入浏览器、队列快照或日志。全局管理员 Cookie 不代表房间内所有成员各自拥有对应播放权益。

实施顺序

阶段交付进入实现的条件
1. Bandcamp spike按普通 Subsonic 来源配置，核对现有 search3.view、单曲信息、封面和 stream.view。Beta 面向账号收藏。Bandcamp 公告验证专用凭据、收藏范围、格式、拖动，以及账户授权是否覆盖房间使用。兼容则走现有来源管理。
2. SoundCloud用官方 Widget 完成首个嵌入播放，搜索凭据可用后接入目录。用 READY、实际播放状态、位置和 FINISH 驱动现有房间同步。Widget API验证可嵌入单曲、自动播放受阻后的恢复、进度回调、不可播放状态与正确的队列推进。
3. YouTube保留 Data API 搜索，用官方 IFrame Player 播放。待嵌入路径通过验收后，再单独处理旧媒体路由。IFrame Player API确认可见播放器和最小 200 × 200 视区，验证不可嵌入视频和各客户端兼容性。先评审静态播放器布局方案，再改页面。
4. QQ 音乐 SDK spike固定 @sansenjian/qq-music-api 版本；Node sidecar 只提供 Go 所需的搜索/解析接口，Go 适配后接现有媒体代理。先使用匿名 SDK 能力，不依赖单曲详情 API。目标部署出口搜索稳定；授权确认可共享；完整音频、HTTPS Range、短期 URL 续期通过；不缓存整曲、不泄露 Cookie/URL。无播放权益时明确拒绝入队。
5. VK Audio 实验确认 VK 音频授权接口与样例，复用原生音频路径；不实现 VK Video iframe。完整音频、Range、签名有效期与房间权限清楚后才继续。

从 SoundCloud 阶段起再扩展 SQLite 队列、Go 播放快照及前端解析，让载荷区分原生音频和嵌入播放。旧队列缺新字段时按原生音频读取。嵌入载荷只带平台 ID 或校验后的官方引用。前端播放器实现加载、播放、暂停、定位、读位置和卸载，房间仍由 Go 维护播放时钟并决定何时换曲。QQ/VK 音频解析结果仅作为原生音频来源，不把上游短期地址写入持久队列。发布前检查 Web 与桌面 API 消费方，按实际播放器能力启用嵌入来源。

首批验收

  • 媒体契约。 用本地测试源覆盖首包、远端 Range、越界 Range、上游签名过期后的有限重试和无权访问。检查媒体请求和下一首准备都不会提交 VK 全文件缓存。
  • 双客户端播放。 用两名房间成员验证入队、播放、暂停、拖动、晚加入、重连、切歌和自然结束。核对当前曲目和 playEpoch，记录定位后两端的位置误差，确认曲目只推进一次。真实样例阶段加入 Safari/iOS 检查。
  • 故障归属。 一个成员的自动播放受阻或访问失败时，其余成员可继续当前曲目。曲目级错误按现有服务端裁决处理。若测试触发时钟拥有者错误导致误跳，先收紧该错误映射，再启用 VK 来源。
  • QQ 音乐。 覆盖搜索无结果、付费曲无 URL、完整音频、上游 500001、Range、过期地址有限重解析、sidecar 不可用及实际部署网络。Cookie 默认关闭；启用时验证权限、过期/替换/清除/重启，所有日志、响应和队列快照不含凭据或短期上游 URL。不得以匿名样例成功替代授权审查。
  • 交付范围。 先用本地可控样例验证代理和同步，再分别用获授权的 VK 音频与 QQ 音乐曲目验证上游行为。当前交付仅为分析和实施计划，真实部署出口、内容授权及双客户端结果均待后续验证。
